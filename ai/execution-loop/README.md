# День 5. Codex Execution Loop

## Цель

Провести один автономный прогон Codex по пулу из 15-20 задач и подготовить отчет по факту прогона.

Главная метрика: сколько задач Codex выполнит подряд без вмешательства пользователя.

## Pre-run gate

Перед запуском прогона остановись и напомни пользователю:

```text
Перед запуском execution loop нужно накидать 15-20 задач в backlog: ai/execution-loop/day5-task-pool.md.
```

Не запускай loop, пока backlog не заполнен задачами с понятным критерием готовности и локальной проверкой.

## Как запустить прогон

1. Заполни `day5-task-pool.md` 15-20 реальными задачами.
2. Убедись, что у каждой задачи есть тип, критерий готовности и ожидаемые проверки.
3. Открой новую задачу Codex в этом репозитории.
4. Передай Codex стартовый промпт ниже.
5. После старта не вмешивайся в прогон до остановки loop.

Стартовый промпт:

```text
Запусти День 5 Codex Execution Loop по правилам из ai/execution-loop/README.md.

Перед стартом проверь pre-run gate. Если backlog ai/execution-loop/day5-task-pool.md не заполнен 15-20 реальными задачами, остановись и напомни, что сначала нужно накидать задачи в backlog.

Если backlog готов:
1. Зафиксируй baseline в ai/execution-loop/day5-run-log.md.
2. Бери первую задачу со статусом todo из ai/execution-loop/day5-task-pool.md.
3. Формируй Task Brief.
4. Сам выбирай режим: Bug Fix, Research или task-executor.
5. Выполняй задачу автономно.
6. Для успешно завершенной изменяющей задачи делай отдельный коммит.
7. Обновляй task pool и run log.
8. Переходи к следующей todo-задаче.

Остановись только если все задачи завершены или возникла failure-причина из ai/execution-loop/day5-run-log.md. В финале заполни отчет по одному прогону без упоминания локальной модели или второго запуска.
```

## Артефакты

- `day5-task-pool.md` - backlog задач для автономного прогона.
- `day5-run-log.md` - лог выполнения, метрики и итоговый отчет.

## Роли

### Loop runner

Главный Codex-поток работает как loop runner:

1. Проверяет pre-run gate.
2. Берет первую задачу со статусом `todo`.
3. Формирует короткий `Task Brief`.
4. Классифицирует задачу.
5. Запускает выполнение в подходящем режиме.
6. Фиксирует результат в `day5-run-log.md`.
7. Для успешно завершенной изменяющей задачи делает коммит.
8. Возвращается к следующей задаче.

Loop runner хранит в основном контексте только компактный итог задачи: статус, commit hash, проверки, время и короткую причину проблем.

### Task executor

Каждая небаговая изменяющая задача выполняется в свежем subagent/task-executor, чтобы изолировать контекст.

Task executor получает только:

- исходную задачу;
- `Task Brief`;
- релевантные правила из `AGENTS.md`;
- стартовое Git-состояние;
- ожидаемые проверки.

### Bug Fix

Баги выполняются через `ai/profile/bug-fix.md`.

Не добавляй поверх `Bug Fix` еще один произвольный executor-слой: профиль уже управляет стадиями `plan -> execute -> validate -> done`.

### Research

Research-задачи выполняются через `ai/profile/research.md`.

Research-задача не должна менять checkout, создавать отчетный файл, stage, commit, restore, reset или delete.

## Классификация задач

- `bug` - есть текущее поведение, ожидаемое поведение и намерение исправить дефект.
- `research` - нужно ответить на вопрос о коде, структуре, поведении, зависимостях или архитектуре без правок.
- `feature` - нужно добавить небольшое пользовательское или техническое поведение.
- `refactor` - нужно улучшить структуру без изменения поведения.
- `tests` - нужно добавить или уточнить тестовое покрытие.
- `docs` - нужно изменить документацию.

## Task Brief

Перед выполнением каждой задачи loop runner формирует brief:

```markdown
## Task Brief
ID: <id>
Type: <bug | feature | refactor | tests | docs | research>
Mode: <Bug Fix | Research | task-executor>
Goal: <one sentence>
Done criterion: <clear done/not done criterion>
Allowed scope: <files, modules, or boundaries>
Expected checks: <commands or "Markdown-only">
Start time: <ISO-8601>
Start Git: <HEAD and status summary>
Stop condition: <when to stop and report failure>
```

## Правила автономности

- Пользователь не вмешивается между задачами.
- Не просить подсказок, если задачу можно выполнить через репозиторий и локальные проверки.
- Остановиться и зафиксировать failure, если задача требует внешнего аккаунта, ручного UI-действия, недоступного секрета или архитектурного решения без локального источника истины.
- Не менять staged/unstaged/untracked изменения пользователя вне явно выполняемой задачи.
- Не включать в отчет сравнение с локальной моделью или вторым прогоном.

## Метрики

- `streak` - сколько задач подряд завершено без вмешательства.
- `failed_on` - id задачи, на которой loop остановился.
- `failure_reason` - причина остановки.
- `avg_time_per_task` - среднее время по завершенным задачам.
- `first_pass_rate` - процент задач, где проверки прошли с первой попытки внутри задачи.
